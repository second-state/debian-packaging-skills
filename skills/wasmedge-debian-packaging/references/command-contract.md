# Four intents, one candidate

## Harness-neutral user intents

The following are workflow intents, not required commands. A harness may expose them as slash commands, chat actions, buttons, API calls or ordinary conversation. The mapping must be documented by that host and must not alter the semantics:

- `draft [version/series]`: prepare a candidate ready for review.
- `status`: read-only candidate status.
- `resume`: continue an unchanged candidate after live identity checks.
- `publish`: preview and, only after exact human approval, submit the reviewed candidate.

An explicit bare invocation of this skill means `draft`: immediately begin discovery and local preparation. Do not ask a generic task question; ask only unresolved version, identity or material-decision questions after showing the discovered state. `draft` is not merely an import helper, and `publish` is not Debian archive upload. Never execute public actions merely because a host loaded this skill or the word `publish` appeared in a prompt.

Before `draft`, generate the dynamic decision object in decision-contract.md from current sources. Do not ask the user to supply a version if authoritative discovery can enumerate candidates; ask only for the choice after showing evidence.

The assistant owns the workflow. A `draft` request authorizes ordinary local preparation, new local commits and standard validation in the announced isolated workspace. Ask only for unresolved target/identity, material resource costs, destructive operations or substantive owner/maintainer decisions. Publication remains separately authorized. Do not ask the user to choose routine commands, test matrices, directory names or JSON schema. Existing applicable answers are reused, not re-requested at every stage. Automatically select a safe new workspace and standard validation environment; announce them without asking technical preference questions. Ask before deletion or history rewriting.

## Local stage contract

### Portable phase/state contract

- `DISCOVERING`: resolving version, canonical base, workspace and identity candidates.
- `PREPARING`: importing source and Debian packaging.
- `REVIEWING`: semantic packaging, policy, metadata and maintainer-baseline review.
- `VALIDATING`: final-candidate build and applicable tests.
- `READY_FOR_REVIEW`: editable draft, final diff and evidence are bound to one candidate.
- `BLOCKED`: one concrete failure or owner/maintainer decision prevents progress; preserve evidence.
- `PUBLISH_PREVIEW`: exact account, fork, refs, target, title and body are displayed.
- `AWAITING_APPROVAL`: no external effect has occurred; wait for exact human approval.
- `SUBMITTED`/`EXISTING_MR`: verified MR URL and state returned.

`READY_FOR_REVIEW` is invalidated by candidate HEAD/diff/changelog/evidence changes. `status` reports this without re-running work.

Use `scripts/release-workflow.py` to run a durable local plan, generated by the assistant outside the packaging repository. This is internal bookkeeping, not a form for the user. Each command is an argv array, never shell-expanded. Plans contain only already-authorized local operations. Do not embed push/MR/email/upload commands in a local plan. The tool blocks common publication commands as defense in depth, not a security sandbox.

Required stages, in order:

1. **prepare**: environment/identity preflight, canonical base, download/import, exact target version and author assertions. Reuse trusted toolchain caches, not previous candidate artifacts.
2. **review**: source/archive/repack and copyright audit, applicable bugs/policy/watch review, maintainer-baseline comparison, ABI/component scope, actual edits and changelog reconciliation. Assistant performs semantic review and records conclusions; an exit code alone cannot prove licensing or ABI safety.
3. **validate**: build the final candidate, lintian with warning triage, package/runtime/upgrade tests, relevant architecture/ABI checks, and maintainer-required linters. Select scope from package risk and current conventions, not one universal maximal matrix. Record skips with explicit justification; inability to perform required validation is BLOCKED, not success.
4. **handoff**: concise English MR title/body, focused diff, final author/version check, evidence manifest and known limitations. Recheck that tests correspond to the final candidate. No generated build products in commits. Metadata test results must not be replaced by prior trials.

The helper is only stage 1. Never return “done” with a list of feasible unfinished local requirements. Continue ordinary authorized work. Stop only for an actual failure, missing owner-only decision, resource boundary or external dependency; explain one concrete next action and preserve logs.

The runner skips completed commands only when the plan is unchanged and recorded outputs still match. Candidate source changes must invalidate affected review/validation and handoff stages; pass a new plan revision and rerun, rather than adopting an old success record. Evidence outputs should be small stable logs/status files, not transient objects. A plan change requires a new state directory so history is not silently rewritten.

## Recoverable local failures are work, not a user TODO

A runner BLOCKED state means the command attempt stopped; it does not mean the
agent's draft task is finished. On a failed local check:

1. Read the actual command, exit code and diagnostics. Classify packaging/test
   adaptation, upstream defect, environment failure, or missing owner decision.
2. Verify intended behavior against the selected source version and CLI help.
   Do not blindly copy an old fix or hard-code a release-specific workaround.
3. If a minimal local packaging/test/documentation correction is within scope,
   apply it, update the top changelog and perform the affected checks again.
   No new approval is needed for ordinary non-destructive local draft work.
4. Preserve the failed attempt. Generate a recovery plan/new state directory in
   the SAME workspace. Already imported source and installed tools need not be
   downloaded again. Carry forward only evidence bound to unchanged inputs;
   never fabricate fresh pass logs or replay import blindly.
5. Continue to handoff only after relevant checks pass. Stop for the owner only
   when a real authorization, material resource, destructive or policy decision
   is missing, or an upstream/environment blocker cannot safely be resolved.

Keep recovery bounded: after two unsuccessful fixes of the same symptom without
new evidence, report the concrete blocker rather than repeating the same command.
Never lower test expectations, skip tests, or suppress failures to get green.

## Required validation evidence before handoff

Installed-package runtime tests belong INSIDE validate, before handoff. Build and
lintian alone are insufficient. A `runtime: pending` or semantic review pending
result must never be promoted to readiness. Execute the relevant Debian test
scripts or autopkgtest against the built candidate, verify which binary/library
was installed, and record command, actual exit, expected outcome and log digest.
Expected-negative tests must assert rejection and the intended diagnostic, not
mistake every nonzero status for success. Inspect stdout and stderr according to
the actual command contract.

Set the plan's `validation_report` path to the report produced by validate.
The runner automatically calls `scripts/check-validation.py` before handoff.
The assistant constructs this internal report from actual observations, never asks
the user to fill it. Required fields: `semantic_review` = `passed`, and `checks`
containing categories `build`, `lintian`, and `runtime`. Each check contains
`category`, argv `command`, integer `exit_code`, `log` (relative to report or
absolute), and `sha256`. The required build, lintian and runtime checks must
have `status: passed` and exit 0; they cannot be marked `not-applicable`.
Only additional optional categories may use `not-applicable` with a reason.
Report whether lintian covered binary or source packages, the architecture and
build environment. Binary-only lintian results do not establish source-package
lint cleanliness.
Commands wrapping negative probes must return 0 only after asserting expected
failure behavior. This structural guard cannot establish that prose is true;
semantic review must verify candidate identity, adequate test scope and warnings.

## Readiness semantics

READY_FOR_REVIEW means the applicable local checks and semantic review have been completed, evidence is tied to the final candidate, MR text is drafted and remaining limitations are explicitly acceptable for review. It is not upload permission or a guarantee of maintainer acceptance. A structurally completed plan is called LOCAL_PLAN_COMPLETE; the assistant must still audit it before reporting READY_FOR_REVIEW. Do not let a self-written checklist authorize its own correctness.

## Publish contract

When invoked with `publish`, locate the last exact reviewed candidate from its local record. If none exists, finish preparation first. Show source commit, source fork/branch, target project/branch, active **Salsa** account and the exact MR title/body/diff. GitHub authentication is not Salsa authentication. Inspect prior owner approvals; if the same action/content/destination is already approved and unchanged, do not ask again. Otherwise ask one human-only approval covering the named pushes and one MR, explicitly excluding emails, unrelated issues and archive uploads.

Immediately before authorized effects, read canonical HEAD and existing source-branch MRs. If canonical changed, reconcile and revalidate locally; do not force-push or silently switch destinations. If matching MR already exists, return its URL; do not create a duplicate or edit it unless that edit was approved. Query the authenticated Salsa user and verify source/target repositories. Never change credentials automatically.

Perform only approved pushes (including requisite upstream/pristine-tar refs per repository convention), then create the MR via the authenticated Salsa client. Treat ambiguous network failures as unknown: look up the exact source project/branch/target before retrying a create. Verify the resulting MR URL, target, source HEAD and body; return the URL. Do not label archive acceptance complete. Any body update or extra notification needs scope review, not inferred approval.

This task implements and tests the workflow locally; it does not supply standing consent to publish. Future `publish` is a user intent to submit, but existing explicit preview/approval requirements remain in force.

## Acceptance scenarios

- Bare invocation: missing identity/version only, then assistant completes local stages without further technical prompting.
- Helper succeeds but tests fail: BLOCKED with stage/log, no handoff success or public actions.
- Unchanged resume: completed stages not replayed; no repeated identity question.
- Changed plan/output/candidate: old success invalidated, never silently reused.
- Missing Salsa credentials: local result preserved; explain login requirement, do not authenticate on user's behalf.
- Publish denied/cancelled: zero pushes/MR/email/uploads.
- Publish approved exact candidate: approved refs, one MR, verified URL; no archive upload.
- Existing MR or uncertain create response: lookup before retry; never duplicate blindly.
- Final report: short changed/tested/remaining/path summary, not internal JSON or every tool call.

## Internal plan schema

```json
{
  "cwd": "/absolute/local/workdir",
  "inputs": ["candidate-inputs.json", "local-driver.py"],
  "candidate_repos": ["wasmedge"],
  "validation_report": "validation-result.json",
  "stages": [
    {"name": "prepare", "commands": [["python3", "local-driver.py", "prepare"]], "outputs": ["prepare-result.json"]},
    {"name": "review", "commands": [["python3", "local-driver.py", "review"]], "outputs": ["review-result.json"]},
    {"name": "validate", "commands": [["python3", "local-driver.py", "validate"]], "outputs": ["validation-result.json"]},
    {"name": "handoff", "commands": [["python3", "local-driver.py", "handoff"]], "outputs": ["MR-DRAFT.md", "candidate-result.json"]}
  ]
}
```

Execute with `python3 scripts/release-workflow.py --plan <plan.json> --state-dir <run-state>`. The assistant supplies real commands/driver and reviewed assertions; this example is not an installed driver. Input files must bind the source/base, exact skill/helper and driver versions and environment assumptions. Snapshot records alone cannot detect an unrecorded working-tree edit: the driver must recheck actual candidate tree identity before accepting reuse or publication. Do not claim the runner implements packaging semantic checks itself.

## Submission adapter

Use `python3 scripts/submit-mr.py --plan <submission.json> --state-dir <candidate-submission-state>` for read-only preflight/preview. Requires an existing reviewed Salsa fork, `glab` authenticated to salsa.debian.org, SSH push access and a clean committed candidate. If the fork is absent, explain and obtain explicit fork-creation approval; the adapter does not create it. Do not install/login/switch credentials silently.

The assistant generates submission.json with repo, source_project, target_project, source_branch, target_branch, full head/base commit IDs, account, title, body, ready_report (absolute path), ready_report_sha256 and optional supporting_refs [{ref, sha}]. Every supporting ref must be explicitly included in the reviewed push scope; no wildcard refs. The readiness report has status READY_FOR_REVIEW, exact head/base and evidence [{path, sha256}], with absolute paths to retained logs and semantic review. Generate it only after the complete readiness audit; neither JSON nor its digest proves user permission.

After verifying the original owner's approval of the preview's exact candidate/account/destination/content, invoke with `--approved-plan-sha256 <preview digest>`. This flag is ONLY an exact-plan guard, not authentication or an authorization receipt. Never synthesize human consent from a digest, local file or delegated answer. The assistant must enforce the owner boundary before this command. The adapter verifies clean HEAD, pinned evidence, current Salsa user/base, exact refs and existing MRs, performs a non-force atomic push, creates at most one MR per invocation and verifies the result. An uncertain create response triggers lookup, not another POST. A returned EXISTING result is not a new submission and must be reported with its state; differing existing text is not overwritten.

Transport tests use fake Git/GitLab responses; they do not prove live credentials, server permissions, availability or network race freedom. Canonical advancement after preflight may still require maintainer/revalidation work. No real publication is needed to test this feature, and development permission is not permission to publish a fixture MR.

Keep the same candidate submission state directory across retries. A lock prevents parallel creates. A durable creating/unknown record blocks another POST when the MR cannot yet be found; inspect server state rather than deleting the journal to retry. A matching existing MR is returned read-only. Lock/journal recovery requires checking the original operation, not guessing it failed.

The runner rechecks live candidate HEAD, tracked diff and untracked file contents before any stage reuse. Declare candidate_repos even if prepare will create them. Each successful stage records the new identity; unrecorded mutation invalidates reuse. Git push disables inherited followTags, push options and submodule recursion; approval covers exact refs only.

Submission refuses repositories with Git URL insteadOf/pushInsteadOf configuration rather than risking a different destination from the preview. This conservative check may block unrelated rewrites; explain the issue and use an explicitly reviewed configuration/environment, never silently modify global configuration.

## Stable user-facing completion

Return one compact result: READY_FOR_REVIEW with version/workdir and relevant test warnings; BLOCKED with one actionable cause and retained log; or SUBMITTED/EXISTING with verified MR URL and state. Do not report intermediate helper success as final. Publication consent applies to the exact reviewed plan, not a new candidate after failures. A live MR is not created during UX acceptance tests.

## Implementation scope

This remains an agent skill, not a standalone universal Debian packager. The assistant generates local commands and performs source/packaging judgment using these references; scripts provide stable execution/evidence and submission transport. Users never supply plans or JSON. Complex upstream failures remain genuine blockers, not uncertainty to hide. Local stage completion does not auto-generate readiness assertions. No claim is made that every package can be prepared unattended or that tests simulate all model behavior.


## Host adapter requirement

A host adapter should pass an explicit bare skill invocation through as the
user's `draft` request rather than converting it into an empty generic prompt.
If the host cannot execute tools from a skill invocation, it must report that
limitation; it must not imply that preparation occurred. The core skill remains
harness-neutral across slash commands, buttons, API calls and conversation.
